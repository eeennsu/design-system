## 0. 질문의 층위 정리

사용자 질문은 3단계였고, 각 단계의 답이 다음 질문을 만들었다.

| 단계 | 질문 | 답 | 근거 |
|---|---|---|---|
| ① | 프로젝트마다 디자인 방향이 다른데 DS가 감안하나? | 부분. 색은 브랜드 축(C-5a)과 `className`(C-15)으로 커버. 밀도·타이포 스케일·컴포넌트 형태 같은 "방향성"은 전 브랜드 공유라 미커버 | C-5a "간격·타이포 스케일은 전 브랜드 공유", AC-6a |
| ② | 소비 프로젝트가 DESIGN.md를 만들면 DS가 인지·반영하나? | 아니다. agent-native는 v2 보류. DS가 노출하는 건 `.d.ts`(AC-18)뿐. DESIGN.md는 소비 프로젝트에서 클로드코드가 읽는 컨텍스트이지 DS 메커니즘이 아니다 | Topology agent-native 행, Non-Goals "MCP 서버 / 에이전트 전용 레이어" |
| ③ | 그러면 특화 디자인 통로를 열어야 하지 않나? | 연다. 단 "어느 층위를"이 문제 — 아래 1절 | — |

②는 R22에서 다시 열지 않았다. DESIGN.md → 브랜드 파일 생성 같은 에이전트 워크플로는 DS 밖의 일이고, 그 결과물이 들어오는 입구가 C-5b다.

**A를 택한 이유를 한 줄로:** 이미 되는 것을 계약으로 승격하는 것이라 여는 비용이 이름 안정성 하나뿐이고, 어휘 봉쇄와 C-5a 불변 계층을 건드리지 않는다.

**A의 실체에 대한 주의.** "DS 코드 변경 0"은 CSS 채널에 한한 말이다. 계약이 되는 순간 (1) semantic 변수 이름이 minor에서 못 바뀌고, (2) AC-26 테스트가 생기고, (3) 다크 3블록·JS 객체 갭이 알려진 동작으로 고정된다. 공짜가 아니라 싸다.

## 2. A. 기술 확인 — NativeWind v5

출처: context7 `/websites/nativewind_dev_v5` (themes 가이드, `api/vars`, `customization/colors`). 2026-09-05 조회.

| 확인 항목 | 결과 | 스펙 반영 |
|---|---|---|
| `:root` CSS 변수를 런타임 기본값으로 읽는가 | **예.** 테마 가이드: "`@theme` 블록은 Tailwind 클래스 생성용, `:root`는 런타임 기본값" — 웹과 같은 2단 구조 | C-5b RN 항목 |
| import 뒤 `:root` 재선언이 last-wins인가 | **문서에 없음.** `@media ios { :root {…} }`로 플랫폼별 `:root` 값을 두는 예시는 있어 `:root` 블록 복수 선언 자체는 지원 | **C-19 게이트 (6)** 으로 이관. 미지원 시 `VariableContextProvider` 루트 래핑으로 RN 채널 재설계 |
| 런타임 오버라이드 API | `VariableContextProvider`(서브트리 변수 컨텍스트), `vars()`(인라인 style). 둘 다 런타임 전환용 | DS 채널 아님. 런타임 브랜드 전환은 C-5a 범위 밖 → Non-Goal 명시 |
| JS에서 변수 해석값 읽기 | `useUnstableNativeVariable("--name")`. 이름대로 unstable | B-2 |
| `.dark` 루트 셀렉터, `:root:not(.light)` | 기존 게이트 (2)·(4). R22 무변경 | — |

RN 채널을 웹과 같은 CSS `:root` 3블록으로 두는 이유: 소비자가 웹·RN 프로젝트에 같은 CSS 조각을 붙여넣으면 끝이라야 "토큰과 클래스 어휘 공유"(CLAUDE.md 범위)가 오버라이드까지 이어진다. `VariableContextProvider`를 DS 채널로 삼으면 RN만 JS 코드가 필요해 채널이 2개가 된다.

## 3. B. 사람 결정 2건

### B-1. 통로 선택 [C-5b · Non-Goals]

**택: A. 단 RN 확인 먼저.**

- 사용자가 "A 반영하되 RN 확인 먼저"를 선택. 확인 결과는 2절
- RN 확인에서 새로 나온 것: import 순서 캐스케이드 미명시(게이트 (6)), JS 객체 갭(B-2)
- 되돌리기: **중**. 채널을 계약에서 빼도 CSS는 계속 동작하므로 소비자 코드는 안 깨진다. 깨지는 건 이름 변경 시뿐 — 그래서 의무가 "이름 안정성"으로 좁혀진다

### B-2. JS 토큰 객체 갭 [알려진 동작 11]

**택: ① 알려진 동작으로 기록. 훅 제공 안 함.**

갭의 실체: 소비자 CSS 오버라이드는 `@<scope>/tokens`의 RN JS 객체(AC-4)에 닿지 않는다. JS 객체는 빌드 산출물이라 항상 import한 브랜드 파일 값이다.

| | ① 알려진 동작으로 기록 | ② `useToken()` 훅 제공 |
|---|---|---|
| v1 DS 코드 영향 | **없음.** v1 DS 코드가 JS 객체를 읽는 곳은 RN Text 폰트 폴백(C-19 (5))뿐이고 타이포는 오버라이드 대상이 아니다. Reanimated를 쓰는 RN 오버레이는 v2 | 없음 (같은 이유) |
| 소비자 영향 | 소비자 자기 Reanimated 코드가 JS 객체 색을 읽으면 오버라이드 전 값. 필요하면 `useUnstableNativeVariable` 직접 사용 | 소비자가 DS 훅으로 해석값을 읽는다 |
| 의존 | 없음 | NativeWind preview의 unstable API에 DS 공개 계약이 얹힌다. API 이름·시그니처가 바뀌면 DS major |
| 되돌리기 | 나중에 훅 추가는 추가적 | 훅 제거는 파괴적 |
| 판정 | **채택** | 탈락. 나중에 안정화되면 추가적으로 넣을 수 있다 |

### 명시적으로 열지 않은 것

- **간격·타이포 브랜드별 분리(C)** — 1절. Non-Goal
- **소비자 `@theme` 확장(B)** — 1절. Non-Goal
- **primitive 변수 오버라이드** — 기술적으로 된다. 계약 밖으로 두고 이름 안정성을 보장하지 않는다(알려진 동작 13). 이유: primitive를 계약에 넣으면 팔레트 재편이 major가 된다
- **DS가 오버라이드 가능 변수 목록을 별도 문서로 제공** — 안 한다. `twMergeConfig` 색 키와 1:1이라 빌드 산출물이 곧 목록이다. 문서를 따로 두면 드리프트한다
