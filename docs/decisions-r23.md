## 0. 질문 ①의 정정 — 통로는 규약 수정이 아니다

사용자가 C-5b를 "소비 프로젝트가 DS 규약을 수정하는 것"으로 읽었다. 아니다. C-5b가 여는 것은 CSS 변수 **값**의 재선언 하나뿐이다.

| 소비 프로젝트가 바꾸는 것 | 소비 프로젝트가 못 바꾸는 것 |
|---|---|
| `:root`의 semantic 색 변수 **값** | 클래스 어휘 (새 클래스 생성은 Non-Goal, C-15) |
| | 컴포넌트 API — `variant` · `size` · `tone` 열거 (C-14) |
| | `size` 5단 계약, 간격·타이포·radius·shadow 스케일 (C-5a 불변 계층) |

계약·타입·클래스 이름은 전부 그대로다. 그래서 "DS 코드 변경 0"이 성립했다. 이 정정은 스펙 변경을 낳지 않는다 — C-5b 본문이 이미 그렇게 쓰여 있다. 오해가 재발하지 않도록 여기 남긴다.

## 1. 질문 ②의 검토 — 클로드코드가 어디까지 커버하나

사용자 논지: 화면은 클로드코드가 소비 프로젝트의 DESIGN.md를 읽고 DS에서 값을 가져와 만든다. 그러면 앱마다 다른 디자인은 자동으로 나오는 것 아닌가.

**부분적으로 맞다.** 층위를 갈라야 답이 나온다.

| 층위 | 클로드코드가 커버하나 | 근거 |
|---|---|---|
| 화면 구조 · 정보 위계 · 컴포넌트 선택 | **예.** DS 밖의 일이라 DS가 할 게 없다 | — |
| 간격 리듬 — 열거된 간격 중 무엇을 고르는가 | **예.** 앱 A가 `mt-2`/`mt-4` 위주, 앱 B가 `mt-8`/`mt-12` 위주면 밀도 인상이 실제로 갈린다 | C-7a 희소 열거 10단 |
| 색 | **예.** C-5b 채널로 앱 단위 주입 | C-5b |
| 컴포넌트 내부 — Button 높이·패딩, Card radius, Input 테두리 | **아니다** | C-5a 불변 계층, `size` 5단 계약 |

②의 핵심 반론은 마지막 행이다. 클로드코드가 컴포넌트 내부 형태를 앱마다 다르게 하려면 **호출 지점마다** `className="rounded-[2px] py-1.5"`를 쓴다. 동작은 한다(알려진 동작 3 임의값 탈출구, AC-11 twMerge 승리). 문제는 앱 전역 결정을 파일 수십 개에 반복해 쓴다는 것이고, 하나를 빠뜨려도 잡는 테스트가 없다는 것이다. 그건 이 레포가 없애려는 shadcn 복붙 드리프트와 같은 모양이다(CLAUDE.md 목표).

**DESIGN.md의 지위는 R22에서 안 바뀐다.** DS 메커니즘이 아니라 소비 프로젝트에서 클로드코드가 읽는 컨텍스트다(R22 0절 ②). 그래서 DESIGN.md가 있다는 사실만으로 DS가 할 일이 줄지는 않는다 — DESIGN.md가 지시할 수 있는 범위가 곧 DS가 연 채널의 범위다.

**결론: 걱정은 유효하다.** 다만 유효 범위가 좁다 — 색·간격 리듬·구조는 이미 갈리고, 안 갈리는 것은 컴포넌트 내부 형태(radius·컨트롤 높이·테두리)와 폰트 패밀리다.

## 2. 확대안 C-5c와 R22 후보 C의 구분

R22 Non-Goals가 닫은 것은 **후보 C**다. C-5c는 다른 것이며 R22에서 검토된 적이 없다. 혼동하면 "이미 닫힌 결정"으로 잘못 처리된다.

| | C-5c. 오버라이드 **대상** 확대 | C. 스케일 자체의 브랜드별 분리 (R22 Non-Goal) |
|---|---|---|
| 무엇을 바꾸나 | 계약에 들어가는 변수 목록을 색 → 색 + `--radius-*` + 폰트 패밀리로 넓힘 | 간격·타이포 **스케일 구조**를 브랜드별로 다르게 함 |
| 스케일 열거 | 불변. `--radius-md`가 계속 존재하고 값만 앱별로 다름 | 열거 자체가 브랜드마다 달라짐 |
| `size` 5단 계약 | 무영향 | 재설계 |
| C-7a 간격 열거 10단 | 무영향 | 충돌 |
| AC-6a("브랜드 교체 시 색만") | 문구 수정 필요 | 폐기 |
| 여는 비용 | 이름 안정성 의무가 1종 → 3종 | 토큰 빌드·브랜드 파일·`size` 매핑 재설계 |
| 상태 | **연기(트리거 조건부)** | **Non-Goal 유지.** 트리거와 무관하게 v1·v2 모두 열지 않는다 |

## 3. B. 사람 결정 2건

### B-1. C-5c를 지금 여는가 [C-5b · Non-Goals · R23 개정 요약]

**택: ② 지금 열지 않는다. 트리거 조건부로 연기.**

| | ① 지금 C-5c를 연다 | ② 트리거 조건부 연기 |
|---|---|---|
| 근거의 성질 | 추측. 앱을 **0개** 만든 상태에서 "5개가 똑같아질 것"을 가정 | 증거를 만든 뒤 판단 |
| 비대칭 | — | **나중에 대상을 넓히는 것은 추가적(additive)이다.** 변수는 이미 존재하고, 계약에 넣기 전까지 아무도 그 이름 안정성에 기대지 않으므로 깨질 소비자가 없다. minor로 들어간다 |
| 반대 방향 비용 | 넣었다가 빼는 것은 이름 안정성 의무를 진 뒤라 파괴적 | 없음 |
| 지금 무는 비용 | 이름 안정성 의무 3종 + AC-6a 문구 수정 + AC-26 확장 + 추측으로 늘린 계약 표면 | 0 |
| 기다리는 비용 | — | **0.** 위 비대칭 때문 |
| 판정 | 탈락 | **채택** |

기다리는 비용이 0이고 지금 무는 비용이 0이 아니므로 다른 기준을 볼 필요가 없다.

부수 근거 하나: 앱 5개가 전부 사용자 1인의 것이고 포트폴리오다. "전체가 일관된 손맛"이 결함이 아니라 자산일 가능성이 실재한다. 이건 만들어 보기 전에는 알 수 없다.

**트리거(스펙 C-5b에 기록).** DS v1 완료 후 도메인이 다른 소비 프로젝트를 2개 구축한 시점에, 두 앱이 **색 이외의 인상에서 구분되지 않는다**고 사용자가 판단하면 C-5c를 연다. 판단 주체는 사용자 1인이며 자동 기준은 두지 않는다 — 자동 기준을 만들려면 "디자인이 얼마나 다른가"를 수치화해야 하는데 그건 유지보수 표면만 늘린다. 트리거가 충족돼도 후보 C는 열지 않는다(2절).

### B-2. 폰트 패밀리 갭 [알려진 동작 14 · 계획 태스크]

**택: ① 토큰 인벤토리에서 함께 결정. 지금 계약에 넣지 않는다.**

갭의 실체: 앱 성격의 상당 부분이 폰트인데, C-5b 계약 대상은 semantic 색뿐이라 앱마다 폰트를 바꾸는 공개 통로가 없다. `--font-*` 패밀리는 리셋 대상이 아니라 DS `fontFamily` 토큰으로 덮어쓰는 값이다(C-6 리셋 범위).

기술적으로는 색과 같은 캐스케이드로 동작할 **가능성이 높다** — Tailwind v4에서 `@theme`(비-`inline`) 변수는 `:root`에 CSS 변수로 남고 유틸리티가 `var()`로 참조하므로, 소비자가 import 뒤에 재선언하면 이긴다. `--radius-*`도 같다. 다만 **토큰 빌드가 어느 범위에 `@theme inline`을 쓰는지에 달려 있고 그건 아직 안 정해졌다.** 그래서 단정하지 않고 계획 태스크 "토큰 인벤토리"의 확인 항목으로 넘긴다. RN 쪽은 C-19 게이트 (6)이 이미 같은 질문을 담고 있다.

지금 계약에 넣지 않는 이유는 B-1과 같다(추가는 추가적). 대신 인벤토리 단계에서 **이름을 계약 후보로 취급해 짓는다** — 나중에 공개해도 되는 이름으로. 이건 어차피 해야 할 작업 안이라 추가 비용이 0이다.

### 명시적으로 열지 않은 것

- **후보 C 스케일 브랜드 분리** — 2절. Non-Goal 유지, 트리거 대상 아님
- **소비자 `@theme` 확장(후보 B)** — R22에서 닫힘. R23 무변경
- **DESIGN.md를 DS가 읽는 구조** — R22 0절 ②에서 닫힘. agent-native v2 보류. R23 무변경
- **"디자인이 충분히 다른가"의 자동 검증 AC** — 두지 않는다. 수치화 불가이며 유지보수 표면만 늘린다. 트리거는 사람 판단이다
- **컴포넌트 내부 형태를 바꾸는 prop**(`radius="none"` 등) — C-14 위반. 열거 prop을 늘리는 것은 C-5c와 별개 경로이며 검토하지 않았다
