# R26 결정 기록 (2026-09-25)

spendback(`../spendback`)을 에뮬레이터로 본 사용자가 "디자인이 애매하다"고 했다. 앱 브랜치 `exp/toss-look`에서 토스 앱의 인상을 참고해 글꼴 · 색 · 모서리 · 글자 스텝 · 카드 구성을 바꿔 봤고, 사용자가 결과를 채택했다. 이 문서는 그 실험을 DS base로 옮기면서 고른 것과 버린 것을 적는다. 스펙 본문은 결과만 싣는다(스펙 "R26 개정 요약"). 판단 기준은 R21과 같다 — 확정 사항 불변, 되돌리기 쉬운 쪽, 유지보수 표면이 작은 쪽, 타입 · 테스트로 자동 강제되는 쪽.

- 입력: spendback 실험 커밋 `6d7d0d3`(앱 `global.css`의 C-5b 재선언 + 계약 밖 `@theme` 값 덮기 + DS 텍스트 컴포넌트 `font-sans` 패치), 에뮬레이터 라이트 · 다크 화면, 사용자 결정 2건(아래 1 · 4)
- 토스는 **인상의 참고**다. 토스 디자인 시스템의 API · 컴포넌트 · 이름을 가져오지 않는다(Non-Goals "레퍼런스 DS에서 API 규약 차용" 그대로). 값은 DS 대비 기준(글자 4.5:1)을 먼저 지키고 그 안에서 가장 가까운 값을 골랐다. 브랜드 이름은 `base` 그대로다
- 닫힌 결정(R21~R25)과 C-5c는 열지 않았다. 스케일 **구조**(간격 열거, `size` 5단)는 그대로이고 **값**만 바뀐다

## 1. 토스풍을 넣는 곳

| 안 | 내용 | 판정 |
|---|---|---|
| A. 기본값은 품질만, 토스 색은 프리셋 | 글꼴 · 스텝 · 모서리 · 모양은 base에, 파랑 · 회색은 `themes/toss.css` 또는 앱 C-5b | 탈락 |
| **B. base 자체를 토스풍으로** | 색까지 base에 넣는다. 앱은 메인 색(brand 짝)만 C-5b로 지정한다 | **채택(사용자 결정)** |
| C. C-5c만 열고 값은 앱마다 | DS는 radius · 글꼴 통로만 연다 | 탈락 |

- B는 새 계약이 필요 없다. 앱이 메인 색을 지정하는 것은 이미 있는 C-5b다
- R23의 걱정(여러 앱의 인상이 한 축으로 모인다)은 여기서 받아들인다. 앱마다 갈리는 것은 색과 화면 구조이고(알려진 동작 14), 같아지는 것은 컴포넌트 모양과 글꼴이다. 그 공통 부분을 이 수준으로 올리는 것이 사용자가 원한 방향이다
- 모양까지 다른 앱이 필요해지면 그때 C-5c를 연다. 조건(C-5b R23)은 그대로 둔다
- A는 프리셋 이름에 다른 회사 이름이 들어가고, 공개 npm 패키지에 그 이름을 싣는 것이 부담이다. C는 다음 앱이 같은 작업을 반복한다
- 앱이 지정하는 "메인 색"은 `--bg-brand` · `--bg-brand-hover` · `--fg-on-brand` · `--fg-brand` 네 개를 짝으로 본다(C-5b R25 짝 대비의 연장). 회색 단계와 danger는 DS가 갖는다

## 2. 바탕 층

| 안 | 판정 |
|---|---|
| **canvas gray-100 · surface 흰색** — 회색 바탕 위 흰 카드. 실험에서 인상을 가장 크게 바꾼 것 중 하나 | **채택** |
| canvas 흰색 유지, 카드 화면만 앱이 canvas를 재선언 | 탈락 — 사용자가 고른 인상이 기본값이 아니게 된다 |

- 흰 바탕 화면이 필요한 앱은 `--bg-canvas`를 surface 값으로 재선언한다(C-5b, 한 줄). 그러면 Card의 경계가 사라진다 — Card는 테두리 없이 명도 차이로만 구분되기 때문이다(알려진 동작 24)
- 다크는 zinc-950 위 zinc-900이다(1.12:1). 토스 다크처럼 층이 약하게 보인다

## 3. 채움 톤

입력 칸과 칩은 테두리 대신 채움으로 보인다(11). 채움 색 하나가 canvas(회색)와 surface(흰색) 양쪽에서 보여야 한다.

| 안 | canvas 위 | surface 위 | 판정 |
|---|---|---|---|
| surface-muted = gray-100(실험 값) | 1.00 — 안 보인다 | 1.10 | 탈락 |
| **surface-muted = gray-200** | 1.12 | 1.24 | **채택** |

- 실험은 입력 칸이 흰 시트 안에만 있어서 gray-100으로 충분했다. DS 기본값은 Form이 canvas에 바로 놓이는 경우(AC-16 로그인 화면)도 받아야 한다
- 채움 대비는 비텍스트 3:1 대상으로 보지 않는다. 입력 칸은 라벨로 식별되고 포커스 때 brand 테두리가 생긴다. 0.3.0의 입력 칸 테두리(1.47:1)와 같은 판단이다(decisions-r25 "열지 않은 것")
- 결과로 secondary Button · Badge 배경도 gray-200이 된다. hover는 gray-300

## 4. brand

토스 파랑 `#3182F6`은 흰 글자와 3.71:1이라 버튼 글자(16px 400, 4.5:1 기준)를 못 받는다.

| 안 | 흰 글자 | 판정 |
|---|---|---|
| `#3182F6` 그대로 | 3.71 | 탈락 |
| Tailwind blue-600(0.3.0 base) | 5.2 | 탈락 — 채도가 높아 실험에서 고른 색과 다르다 |
| **`#206FEA` = 새 primitive `blue-550`** — 흰 글자 4.5:1을 넘는 가장 밝은 값 | 4.64 | **채택** |

- hover · 글자용은 `#1B64DA` = `blue-650`(흰 글자 5.41)
- 이름은 명도 위치를 따랐다(blue-500 62.3% · 600 54.6% 사이에 56.8%, 600 · 700 사이에 53.2%). 채도는 이웃보다 낮다. primitive는 이름 안정성을 약속하지 않는다(알려진 동작 13)
- **다크도 같은 파랑 + 흰 글자다(사용자 결정).** 0.3.0 base 다크는 밝은 파랑 + 검은 글자였고, 실험 1차도 그랬는데 토스 느낌이 약했다. 대가는 5에 적었다

## 5. 글자용 색 분리 — `fg.brand` 신설, `fg.danger` 별칭 해제

진한 채움 위 흰 글자 4.5:1과 어두운 표면 위 글자 4.5:1은 한 값으로 동시에 맞출 수 없다. 다크에서 `blue-550`은 흰 글자와 4.64인데 zinc-900 위 글자로는 3.57이다. 흰 글자를 받으려면 휘도가 약 0.18 이하여야 하고, 어두운 표면 위 글자는 약 0.25 이상이어야 해서 범위가 겹치지 않는다. 빨강도 같고, 라이트에서도 회색 canvas 위 red-600 글자는 4.33이다.

| 안 | 판정 |
|---|---|
| **채움과 글자를 다른 변수로** — `fg.brand` 신설, `fg.danger`는 `bg.danger` 별칭을 풀고 자기 값을 갖는다 | **채택** |
| 다크 brand를 밝게(0.3.0 방식) | 탈락 — 사용자가 진한 파랑 + 흰 글자를 골랐다 |
| 글자로 쓰는 곳을 금지(문서 규칙) | 탈락 — 강제 수단이 없다. `text-brand`는 이미 쓰이고 있다(spendback) |

- `fg.brand`: base 라이트 blue-650(canvas 4.92), 다크 blue-400(zinc-900 6.72). bakery 라이트 amber-700(amber-50 4.87), 다크 amber-400
- `fg.danger`: base 라이트 red-700(canvas 5.83), 다크 red-400(zinc-900 6.13). bakery는 0.3.0 해석값 그대로(red-600 · red-500)라 모양이 바뀌지 않는다
- 클래스는 `text-fg-brand`(`@theme inline` `--color-fg-brand`)다. `text-brand`는 채움 색이라 글자로 쓰면 다크에서 기준에 못 미친다(알려진 동작 27). `tone`에 `brand`를 넣지 않는다 — C-8의 판단(추가는 추가적, 지금은 이유가 없다) 그대로이고 `text-fg-brand` 클래스로 충분하다
- **C-8 문구가 바뀐다.** "`variant`와 `tone`의 `danger`는 같은 semantic 색"은 같은 **개념**으로 읽고, 값은 채움(`bg.danger`)과 글자(`fg.danger`) 둘을 갖는다. plan D-3의 별칭은 `border.focus` 하나로 줄어든다
- C-5b 계약 표면이 하나 늘어난다(`--fg-brand`). 추가는 추가적이다. `fg.danger`가 별칭이 아니게 되면서 소비자가 `--bg-danger`만 덮으면 글자 빨강은 따라가지 않는다 — 짝 대비 규칙(C-5b R25)에 `fg.brand` · `fg.danger`를 더한다
- `@theme inline` 색이 16개에서 17개가 된다

실험 값(`#6B7684`)은 흰 표면 위에서만 쟀다. 회색 canvas와 채움이 기본이 되면서 한 단계 진해졌다. 다크는 zinc-400(zinc-950 7.56, 채움 zinc-800 5.66)이다.

## 7. 다크 중립색

Tailwind gray는 푸른 기가 있다(hue 약 260). 실험의 다크는 푸른 기가 거의 없는 값(`#101013` · `#1E1E24`)이었다. 가장 가까운 Tailwind 램프인 **zinc**를 primitive에 복사해 쓴다(canvas 950 · surface 900 · 채움 800 · hover 700, 글자 100 · 400). 라이트는 gray 그대로다 — 토스의 회색 단계도 푸른 기가 있고, Tailwind gray와 거의 같다(gray-100 `#F3F4F6` · 토스 `#F2F4F6`).

## 8. 글자 스텝 값

| step | 0.3.0 | 0.4.0 |
|---|---|---|
| sm | 14 / 20 / 400 | 그대로 |
| md | 16 / 24 / 400 | 그대로 |
| lg | 18 / 28 / 500 | 18 / 26 / **600** |
| xl | 20 / 28 / 600 | **22 / 30 / 700** |
| 2xl | 24 / 32 / 700 | **28 / 36** / 700 |

- 5단 구조와 이름은 그대로다. 값만 바뀌므로 R22 후보 C(스케일 구조 분리)와 decisions-r25 "더 큰 표시 글자(3xl)"를 다시 여는 일이 아니다

- RN line-height 배수(D-31)는 빌드가 새 값으로 다시 계산한다

## 9. 모서리

sm 4 · md 8 · lg 12 → **sm 8 · md 12 · lg 16**, **`xl` 20 추가**. 버튼 · 입력 칸은 md(12), 버튼 lg는 lg(16), Card · Dialog는 xl(20)이다. `xl`은 twMerge radius 키에도 더한다. 키 추가는 추가적이다. 이름은 Tailwind 관용이라 C-5c가 열려도 바꿀 일이 없다(R23 요구 (b)).

## 10. Card

| 안 | 판정 |
|---|---|
| **`bg-surface rounded-xl p-6`** — 테두리 · 그림자 없음 | **채택** |
| 0.3.0 그대로(`border` + `shadow-sm` + `p-4`) | 탈락 — 회색 바탕 위 흰 카드 인상이 테두리로 흐려진다 |

경계는 canvas와의 명도 차이뿐이다(라이트 1.10, 다크 1.12). canvas를 surface와 같게 재선언한 앱에서는 Card가 보이지 않는다 — 그때는 `className="border border-border"`를 준다(알려진 동작 24). `card.shadow` 토큰은 소스에서 뺀다.

## 11. 입력 칸 · 칩

| 안 | 판정 |
|---|---|
| **테두리를 투명으로 두고 `bg-surface-muted` 채움**. 포커스 · 오류 테두리는 그대로 | **채택** |
| 테두리를 없앤다 | 탈락 — 테두리 1px이 컨트롤 높이 맞춤(D-6)의 일부다. 포커스 테두리가 생길 때 높이가 흔들린다 |
| 소비자가 className으로 채움 | 탈락 — 실험에서 호출 지점마다 반복했다. R23이 걱정한 복붙 드리프트 그대로다 |

- 칩: 고르지 않은 칩이 `border-transparent bg-surface-muted`, 고른 칩은 그대로(`border-brand bg-brand`). 높이 38 그대로
- 입력 칸 · Textarea: `bg-surface-muted border-transparent`, 포커스 `border-border-focus`, 오류 `border-danger`. 웹은 포커스를 outline으로 그리는 것 그대로다(§4.6)
- `border.default`는 이제 DS 컴포넌트가 쓰지 않는다. 소비자의 구분선 · Card 경계용으로 남는다(gray-200 · zinc-800)

## 12. RN 글꼴

0.3.0의 native 컴포넌트는 글꼴을 지정하지 않아 RN에서 시스템 글꼴(Roboto · One UI)이 나왔다. 웹은 preflight가 `html`에 `--font-sans`를 걸어 Pretendard가 상속된다. RN에는 상속이 없다. 실험에서 인상을 가장 크게 바꾼 항목이다.

| 안 | 판정 |
|---|---|
| **native 텍스트 컴포넌트(Text · Button 라벨 · Chip 라벨 · Badge · Label · Input · Textarea)가 `font-sans`를 갖는다. native 래퍼가 `--font-sans`를 RN 패밀리 이름 하나(`Pretendard`)로 다시 낸다** | **채택** |
| 소비자가 전역으로 지정 | 탈락 — RN에는 전역 기본 글꼴이 없다(`Text.defaultProps`는 React 19 함수 컴포넌트에서 없다). DS 컴포넌트 내부의 라벨에 닿을 방법이 없다 |

- react-native-css는 `font-family` 목록의 첫 이름만 쓴다(`"Pretendard Variable"`). 그래서 native 래퍼가 T-N0(line-height 배수)과 같은 "native만 RN 보정" 경로로 `--font-sans: Pretendard`를 낸다. 값은 토큰 소스의 `$extensions["ds.native"]`(plan §3.6)다
- **소비 앱이 `Pretendard` 패밀리를 등록해야 한다(C-7b, 폰트 파일 미동봉 그대로).** 무게는 글자 스텝이 쓰는 400 · 600 · 700. RN CLI Android는 `res/font/pretendard.xml`(무게별 `<font>`) + `ReactFontManager.addCustomFont(context, "Pretendard", R.font.pretendard)`, Expo는 `expo-font`로 같은 이름을 등록한다(무게별 등록은 SDK 문서를 따른다). 등록하지 않으면 Android는 기본 글꼴로 조용히 떨어진다. iOS는 "Unrecognized font family" 메시지를 낸다고 알려져 있으나 기기에서 확인하지 못했다(알려진 동작 26). 구현 노트에 절차를 둔다
- 이전에는 등록하지 않아도 됐으므로 0.4.0은 RN 소비자에게 설정 한 가지를 더 요구한다. 0.x minor 변경으로 낸다
